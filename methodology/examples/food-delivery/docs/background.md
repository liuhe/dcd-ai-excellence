# QuickBite 需求背景

QuickBite 是一个城市级外卖平台。三类用户通过各自的客户端参与一笔订单：

1. **顾客**在 App 里浏览附近营业中的餐厅，把菜加入购物车，提交订单后跳转支付机构收银台付款。付款成功后能实时看到订单进度，配送中还能看到骑手位置。
2. **商家**在 Web 后台收到新订单提醒，5 分钟内接单，否则系统自动取消并退款。备餐完成后标记"可取餐"，系统随即派单。商家可随时维护菜单与售罄状态。
3. **骑手**在 App 上线后，系统按餐厅 3 公里内就近推送任务，30 秒内接受否则推给下一位。到店点"已取餐"，送达点"已送达"。

**售后**：顾客可对订单申请退款。金额不超过 20 元且骑手未取餐的申请自动通过，其余由客服在运营后台审核。退款通过后调用支付机构退款接口。

**运营**：运营人员在后台看各状态订单数量，重点盯支付后 5 分钟未接单、出餐后 10 分钟未派出的订单。

## 系统划分

| 应用 | 类型 | 职责 |
|---|---|---|
| order-service | 后端 | 订单、支付、退款、菜单的全部写操作与状态流转；发布订单事件 |
| dispatch-service | 后端 | 消费出餐事件，就近匹配骑手，跟踪骑手位置 |
| customer-app | 前端 | 顾客端 App |
| merchant-console | 前端 | 商家后台 |
| rider-app | 前端 | 骑手端 App |
| ops-console | 前端 | 运营与客服后台 |
| payment-gateway | 外部 | 第三方支付机构，不是我们的代码 |

## 关键状态流

订单：Created → Paid → Accepted → Ready → Delivering → Delivered，任一环节可能 Cancelled，送达后可能 Refunded。支付、配送、派单任务各有自己的状态机，在模型里以实体的 `state_machine` 表达。
